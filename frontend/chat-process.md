# 채팅 화면 동작 노트

작성자: 팀원 2
담당 범위: `/chat`, `chat` 컴포넌트, `useChat` 훅

`docs/API_CONTRACT.md`를 화면에서 어떻게 구현했는지, 왜 그렇게 정했는지 남긴 기록입니다.
계약과 코드가 어긋나면 이 문서가 아니라 계약서가 기준입니다.

---

## 1. 파일 구성

| 파일 | 역할 |

| `src/pages/ChatPage.tsx` | 화면만 그린다 |

## 2. 질문 한 번의 흐름

```
사용자가 전송
  │
  ├─ 클라이언트 검증 (빈 입력 / 2,000자 초과)
  │     └─ 걸리면 전송하지 않고 입력창 아래에 오류. 입력값은 유지
  │
  ├─ 질문을 화면 목록에 낙관적으로 추가
  │
  ├─ POST /api/chat  (Authorization: Bearer, 타임아웃 50초)
  │     body: { question, conversation_id? }
  │
  ├─ 201 성공
  │     ├─ 답변을 화면에 추가
  │     ├─ conversation_id를 상태에 보관 (다음 질문에 재사용)
  │     └─ 질문·답변을 sessionStorage에 저장
  │
  └─ 실패
        ├─ 401  → 세션 정리 후 로그인 화면으로 (배너 없음)
        └─ 그 외 → 오류 배너. 저장하지 않음
```

## 3. 오류 처리

### 재시도 버튼 노출 규칙

`docs/API_CONTRACT.md`의 오류 코드 표를 `lib/api.ts`의 `isRetryableError()` 한 곳으로 옮겼습니다.

```ts
error.status === 0 || error.status >= 500
```

| HTTP | 코드 | 재시도 버튼 | 근거 |
|---:|---|:---:|---|
| 401 | `AUTH_REQUIRED`, `AUTH_INVALID_TOKEN` | — | 배너 없이 로그인 화면으로 이동 |
| 422 | `VALIDATION_ERROR` | ✕ | 요청을 고쳐야 하므로 같은 요청을 다시 보내도 결과가 같다 |
| 502 | `AI_SERVICE_ERROR` | ✅ | 서버 측 일시적 실패 |
| 503 | `DATABASE_ERROR`, `DATABASE_UNAVAILABLE` | ✅ | 서버 측 일시적 실패 |
| 504 | `AI_TIMEOUT` | ✅ | 서버 측 일시적 실패 |
| 0 | `CLIENT_TIMEOUT`, `NETWORK_ERROR` | ✅ | 응답을 못 받음. 아래 참조 |

코드를 하나하나 나열하지 않은 이유는, 계약서에 없는 코드가 나와도 같은 규칙이 적용되게 하기
위해서입니다. 실제로 서버 코드에는 계약서에 없는 코드가 여럿 있습니다
(`AI_NOT_CONFIGURED`, `DATABASE_NOT_CONFIGURED`, `INTERNAL_ERROR` 등).

### 응답을 받지 못한 경우 (`status: 0`)

서버가 응답을 준 실패(5xx)와 응답 자체가 없는 실패는 다릅니다.

| | 서버 상태 | 재시도하면 |
|---|---|---|
| 5xx | 서버가 실패를 알려줌 → 저장 안 된 것이 확실 | 안전 |
| status 0 | **알 수 없음** | 이미 저장됐을 수 있음 |

멱등성을 보장하지 않기로 했으므로 이 중복을 막을 방법이 없습니다. 그래서 버튼은 두되
안내 문구를 다르게 해서 사용자가 판단하도록 했습니다.

> 응답을 받지 못했습니다. 질문이 이미 처리됐을 수 있으니 기록에서 확인한 뒤 다시 보내 주세요.

HTTP 상태를 지어내지 않기 위해 `status: 0`을 씁니다. 504로 두면 서버 로그에서 찾을 수 없는
504를 뒤지게 됩니다.

### 401 전역 처리

`lib/api.ts`의 `request()` 한 곳에서 처리합니다. `postChat`과 `fetchMyChats`가 모두 이 경로를
지나므로 `/chat`과 `/history`에 함께 적용됩니다.

```
401 응답 → supabase.auth.signOut()
        → AuthContext가 user를 null로
        → ProtectedRoute가 /login으로 이동
```

`navigate("/login")`을 직접 부르지 않은 이유는, `LoginPage`가 이미 로그인한 사용자를 `/chat`으로
되돌려 보내기 때문입니다. 세션이 남아 있으면 두 화면을 무한히 오갑니다. **문제는 "잘못된 화면에
있는 것"이 아니라 "클라이언트가 아직 로그인 상태라고 믿는 것"** 이므로, 사실을 바로잡으면 이동은
기존 라우팅이 알아서 합니다.

`ChatPage`에는 배너를 띄우지 않는 가드만 있습니다. 없어도 동작은 맞고, 리다이렉트 직전에 배너가
잠깐 보일 뿐입니다.

## 4. 타임아웃

`request()`에서 `AbortSignal.timeout(50_000)`을 겁니다.

50초로 정한 근거는 서버 측 상한입니다.

```
토큰 검증 8s + 문맥 조회 8s + Gemini 25s + 저장 8s = 최악 49초
Vercel maxDuration = 60초
```

짧게 잡으면 정상 처리 중인 요청을 끊게 되고, 멱등성이 없으므로 그 재전송이 중복 저장으로
이어집니다. 그래서 서버 상한보다 길게 잡았습니다.

타임아웃과 네트워크 단절은 `ApiError`로 변환합니다. 그대로 두면 화면에 `Failed to fetch` 같은
영문 메시지가 그대로 노출됩니다.

## 5. 대화 유지와 새 채팅

### 보관 위치

`sessionStorage`에 `conversation_id`와 메시지를 함께 저장합니다.

```
키   b7-1:chat:conversation:<user.id>
값   { "conversationId": "...", "messages": [...] }
```

| 동작 | 유지 |
|---|:---:|
| 새로고침 | ✅ |
| 다른 화면 갔다가 복귀 | ✅ |
| 탭 닫기 / 브라우저 종료 | ✕ |
| 새 탭 | ✕ (탭마다 독립) |
| 「새 채팅」 | ✕ (의도적) |

키에 `user.id`를 넣은 이유는, 로그아웃해도 `sessionStorage`가 지워지지 않기 때문입니다. 같은 탭에서
계정을 바꾸면 이전 사용자의 `conversation_id`로 질문을 쓰게 되고, RLS가 읽기는 막지만 쓰기는 막지
못해 한 대화에 두 사용자의 기록이 섞입니다.

### 성공한 응답만 저장한다

저장 대상은 화면의 `messages`가 아니라 서버가 성공으로 응답한 것만 모은 별도 목록(`confirmedRef`)입니다.

```
질문1 성공 → 화면 [Q1,A1]      저장 [Q1,A1]
질문2 실패 → 화면 [Q1,A1,Q2]   저장 [Q1,A1]
새로고침   → 화면 [Q1,A1]
```

실패한 질문은 서버에 기록되지 않으므로, 저장하면 새로고침한 화면이 실제 기록과 어긋납니다.
`/history`에는 없는데 채팅 화면에는 계속 보이는 상태가 되어, 사용자가 저장됐다고 오해합니다.

### 서버 조회로 복원하지 않은 이유

`conversation_id`만 저장하고 서버에서 메시지를 불러오는 방법도 검토했습니다. 그쪽이 "진실은 서버에"
원칙에 맞지만, **`conversation_id`로 조회하는 API가 없습니다.** `GET /api/me/chats`는 모든 대화가
섞인 평면 목록이라 최근 N개에서 골라내야 하고, 그 범위를 벗어난 메시지는 복원되지 않습니다.

해당 API가 생기면 서버 조회 방식으로 바꿀 수 있습니다. 백엔드에는 이미
`list_recent_context`가 `conversation_id`로 조회하고 있고 인덱스도 있어, 기존 엔드포인트에
쿼리 파라미터를 추가하는 정도로 보입니다.

### 새 채팅

명시적으로 대화를 끊을 수단이 없어 추가했습니다. 요구사항에는 없는 UX 개선입니다.

누르면 화면과 저장값을 비우고, 다음 질문부터 서버가 새 `conversation_id`를 발급합니다.
**기록을 지우지는 않습니다.** 지금까지의 대화는 `/history`에 그대로 남습니다.

## 7. 알려진 한계

- **멱등성 없음** — 응답을 받지 못한 뒤 재시도하면 중복 저장될 수 있습니다. 팀 합의 사항이며,
  프런트는 자동 재시도를 넣지 않고 사용자가 누를 때만 재전송합니다.
- **실패 기록이 남지 않음** — 서버가 실패를 저장하지 않아, 실패한 질문은 어디에도 남지 않습니다.
- **대화 단위 조회 API 없음** — 위 5절 참조.
- **실연동 미검증** — Supabase·Gemini 키를 받지 못해 아래 항목은 확인하지 못했습니다.
  - 로그인 후 질문 → AI 응답이 화면에 표시
  - 비로그인 요청이 401로 차단
  - timeout / API 실패 안내가 실제로 표시
